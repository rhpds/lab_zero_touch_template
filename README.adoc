= Lab Zero Touch Template
:toc: left
:toc-title: Contents

This is the starting point for all RHDP zerotouch labs.
It provides the directory structure, configuration files, and example scripts that the platform expects.
Use this template, customize it, and follow the in-lab modules to build and deploy your lab.

The template itself is a working lab — open it in a deployed environment to walk through the full developer workflow hands-on.

== How to use this template

. Click *Use this template* → *Create a new repository* on the GitHub page
. Clone your new repo and `cd` into it
. Update the four fields in <<_first_things_to_change>>
. Run `utilities/lab-build` and `utilities/lab-serve` to preview locally
. Follow the in-lab modules in order — they teach each layer of the platform

== First things to change

After you create your repository from this template, update these four values before writing any content:

[cols="1,2,2"]
|===
| File | Field | What to set

| `site.yml`
| `title:`
| Your lab's display title

| `site.yml`
| `url:`
| Your GitHub repo URL (e.g. `https://github.com/your-org/your-lab`)

| `site.yml`
| `start_page:`
| `modules::module-01.adoc` — update if you rename your first page

| `content/antora.yml`
| `title:`
| Your lab title (shown in Antora navigation)
|===

[IMPORTANT]
====
`content/antora.yml` has a `name:` field (default: `modules`).
`antora.name` in `ui-config.yml` must use the **same** value.

Antora reads `name:` from `content/antora.yml`; the nookbag UI reads `antora.name` from `ui-config.yml`.
At deploy time the platform merges `user_data.yml` into `content/antora.yml` for **AsciiDoc attributes only** (under `asciidoc.attributes`) — it does **not** replace the component `name:` key.
Do not change `name:` in one file without changing the other.

Advanced: a catalog item can pass a full `ui-config.yml` override (for example `showroom_content_ui_config` in some AgnosticV test configs) — only then can you centralize UI config outside the repo.
====

== Directory structure

[source,shell]
----
.
├── site.yml                    # Antora playbook — title, url, start_page, attributes
├── ui-config.yml               # Module list and tab definitions for the lab UI
├── config/
│   ├── instances.yaml          # VM definitions (image, memory, AnsibleGroup)
│   ├── networks.yaml           # Network attachment definitions (NADs)
│   └── firewall.yaml           # NetworkPolicy rules (additive to platform defaults)
├── content/
│   ├── antora.yml              # Antora component descriptor (name: must match ui-config.yml)
│   └── modules/ROOT/
│       ├── assets/images/      # Images referenced in your .adoc pages
│       └── pages/              # Lab instruction pages (one .adoc per module)
│           ├── module-01.adoc  # Overview
│           ├── module-02.adoc  # Lab infrastructure
│           ├── module-03.adoc  # Setup automation
│           ├── module-04.adoc  # Configuring the UI
│           ├── module-05.adoc  # Runtime automation (live demo)
│           ├── module-06.adoc  # Writing content
│           └── module-07.adoc  # Deploying your lab
├── setup-automation/
│   ├── main.yml                # Ansible playbook — runs once at provisioning time
│   ├── setup-host1.sh          # Provisioning script for the host1 VM
│   └── ansible.cfg
├── runtime-automation/
│   ├── main.yml                # Ansible playbook — runs on each UI action
│   ├── module-NN/              # One directory per module (setup/solve/validation scripts)
│   └── ansible.cfg
└── utilities/
    ├── lab-build               # Build Antora site + extract nookbag UI into ./www/
    ├── lab-serve               # Start local HTTP server on http://localhost:8080
    ├── lab-clean               # Remove ./www/* (clears previous build)
    ├── lab-stop                # Stop the local HTTP server container
    └── lab-check-updates       # Check nookbag SPA and nookbag-bundle for newer releases
----

== Local preview

=== Prerequisites

[cols="1,3"]
|===
| Requirement | Notes

| `podman` or `docker`
| `podman` is preferred and detected automatically. On RHEL/Fedora both are available via `dnf`. On macOS, install https://podman-desktop.io[Podman Desktop] or https://www.docker.com/products/docker-desktop[Docker Desktop].

| `wget`
| Used to download the nookbag UI. Pre-installed on RHEL/Fedora. On macOS: `brew install wget`.

| `unzip`
| Used to extract the nookbag UI zip. Pre-installed on most systems.

| Port 8080 free
| `lab-serve` binds to `localhost:8080`.

| `curl`
| Required by `lab-check-updates` to query the GitHub releases API. Pre-installed on all platforms.

| Linux/amd64 emulation
| `lab-build` runs the Antora container with `--platform linux/amd64`. On Apple Silicon Macs, enable Rosetta in Docker Desktop settings, or run `podman machine init --arch amd64`.
|===

=== Running the preview

[source,bash]
----
utilities/lab-build
utilities/lab-serve
# Browse to http://localhost:8080/
----

NOTE: `lab-build` handles all local-preview differences automatically — tab stripping, `zero-touch-config.yml` aliasing, and `view_switcher` injection.
Open http://localhost:8080/ and the UI is ready.
See `utilities/README.md` for details on what each script does.

Iterative cycle: edit a file → `utilities/lab-build` → refresh the browser.

[source,bash]
----
utilities/lab-stop    # stop the server
utilities/lab-clean   # remove the build output
----

NOTE: `lab-build` caches the nookbag UI zip at `/tmp/nookbag.zip`.
If you see UI issues, delete `/tmp/nookbag.zip` and run `lab-build` again.

=== Alternative: GitHub Pages

A GitHub Actions workflow is included at `.github/workflows/deploy-pages.yml`.
It runs `utilities/lab-build` on every push to `main` and deploys the output to GitHub Pages —
useful for sharing a preview URL with collaborators without running anything locally.

To enable:

. Go to your repo → *Settings* → *Pages*
. Under *Build and deployment*, set *Source* to *GitHub Actions*
. Push to `main` — the workflow runs automatically

The deployed site will be available at `https://<org>.github.io/<repo>/`.

== Development workflow

The recommended order for building a new lab:

. Define your VMs and networks in `config/`
. Test provisioning with the *Developer Experience CI* on https://catalog.demo.redhat.com
. Write provisioning scripts in `setup-automation/`
. Define your module list and tabs in `ui-config.yml`
. Write runtime scripts in `runtime-automation/`
. Write instruction pages (`.adoc` files in `content/modules/ROOT/pages/`)
. Tag a release and add a `common.yaml` to the appropriate AgnosticV repo to deploy

== Deploying to the platform

Add a `common.yaml` to the appropriate AgnosticV repository (abbreviated — see module-07 for the full structure including `__meta__:` and `asset_uuid`):

[source,yaml]
----
__meta__:
  components:
  - name: zt-lab-developer-cnv
    item: zt-rhelbu/zt-rhel-bu-lab-developer-cnv   # or zt-ansiblebu/... for Ansible BU
    parameter_values:
      ocp4_workload_showroom_content_git_repo: https://github.com/your-org/your-lab.git
      ocp4_workload_showroom_content_git_repo_ref: main   # branch for dev; tag for production
----

BU (business unit) developers have self-service merge access, so you can merge your own pull request without approval from another team.
See module-07 in the lab for the full procedure, including the pre-deployment checklist and how `lab-metadata.yml` in the lab repo ties into BU `zt-*-agnosticv` GitHub Actions.
