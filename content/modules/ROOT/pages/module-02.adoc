= Lab infrastructure

The `config/` directory defines the infrastructure for your lab — what VMs exist, what networks they connect to, and what network traffic is allowed.
Define this first. Everything else (scripts, content) is written to match it.

== `instances.yaml`

`instances.yaml` declares the VMs the platform will create using OpenShift Virtualization (CNV).

=== Key fields

[source,yaml]
----
virtualmachines:
  - name: "host1"
    image: "rhel-9.5"       # PVC name in the cnv-images namespace
    memory: "2Gi"            # RAM — must use Gi (gibibytes), not G
    cores: 1
    image_size: "40Gi"       # Minimum disk size — must use Gi, not G
    tags:
      - key: "AnsibleGroup"
        value: "bastions"    # Controls what AgnosticD configures (see below)
    networks:
      - default
----

[WARNING]
====
Use `Gi` (gibibytes), not `G`, for `memory:` and `image_size:`.
The value `2G` is invalid as a Kubernetes resource quantity and will cause provisioning to fail.
====

To see which images are available on the cluster:

[source,bash]
----
oc get pvc -n cnv-images
----

=== AnsibleGroup

The `AnsibleGroup` tag controls which AgnosticD roles run on each VM:

[cols="1,3"]
|===
| Value | What AgnosticD does

| `bastions`
| Full configuration: Satellite registration, common packages, SSH user setup, and a **NodePort SSH Service** in the lab namespace so the VM is reachable from outside the pod network.
Showroom **user_data** (SSH hints for the UI) is built from `groups['bastions'][0]` in the Developer Experience / zerotouch configs — use **exactly one** VM in the `bastions` group so that hostname, NodePort, and wetty auto-login stay unambiguous.
The **default terminal** tab in nookbag auto-SSHs to that bastion (`wetty.ssh.sshHost` from user_data).

| `nodes`
| Same Satellite registration, packages, and SSH user setup as `bastions`, but that VM is **not** the target of the single `*-ssh` NodePort Service created in `infra-openshift-cnv-create-inventory` (only the discovered bastion host gets that Service).
Use for backend VMs that are primarily reached **VM-to-VM** on the default network.
The zerotouch Helm chart still passes **every** instance `name` into `wetty.ssh.sshOtherHosts`, so the showroom pod can run **additional wetty sidecars** per VM — separate from the default terminal tab (advanced; routing is `/wetty_<hostname>` in nginx).

| `isolated`
| No AgnosticD configuration at all.
You own all setup via `setup-automation/` scripts or `userdata:` (cloud-init).
Use when you need full control or a non-RHEL image.
|===

=== `packages:`

For `bastions` and `nodes` VMs, AgnosticD registers to Satellite automatically before installing these packages.
List any additional packages to install at provisioning time:

[source,yaml]
----
    packages:
      - name: nc
      - name: git
      - name: jq
----

=== Multiple identical VMs

Two mechanisms work together:

. **AgnosticV** (when your lab is wired through a BU `common.yaml`) performs a **string** `replace('INSTANCEGUID', guid)` on the raw `instances.yaml` **before** YAML parsing — `guid` is the **deployment** identifier (short alphanumeric), not a per-VM counter.
. **`infra-openshift-cnv-resources`** duplicates an entry when `count:` is greater than `1`: each copy gets `_instance_name` = `name` + `1`, `2`, … **concatenated with no separator** (e.g. `node-` + count `3` yields `node-1`, `node-2`, `node-3` only if your `name` already ends where you expect; `node` + count becomes `node1`, `node2`).

Cloud-init `userdata:` templates still replace the literal `INSTANCEGUID` token with the same **deployment `guid`** on every VM (not a unique suffix per clone).

[source,yaml]
----
  - name: "worker-INSTANCEGUID"   # After AgnosticV replace: worker-<guid>; with count: 3 → worker-<guid>1, worker-<guid>2, worker-<guid>3
    image: "rhel-9.5"
    memory: "2Gi"
    cores: 1
    image_size: "40Gi"
    count: 3
    tags:
      - key: "AnsibleGroup"
        value: "nodes"
    networks:
      - default
----

[WARNING]
====
Pick `name:` carefully when using `count:` — suffixes glue directly to the string.
Avoid ambiguous endings (e.g. a trailing hyphen you did not intend) and remember `INSTANCEGUID` is **not** a numeric VM index in AgnosticV.
====

=== `containers:`

`containers:` defines containers that run inside the showroom pod itself (not as VMs).
Used for custom tooling such as `code-server` or custom terminal images.
For typical labs that only use VMs, leave it empty:

[source,yaml]
----
containers: []
----

== `networks.yaml`

`networks.yaml` defines NetworkAttachmentDefinitions (NADs) for the lab namespace.

[source,yaml]
----
- name: default
# - name: secondary
----

- The `default` entry is *required* — always include it.
- Each entry creates a NAD in the lab namespace using OVN-Kubernetes localnet.
- Names are *GUID-prefixed* at deploy time (e.g. `secondary` becomes `secondary-abc12` in the cluster).
  Reference the bare name (without GUID) everywhere in `instances.yaml`.

=== Secondary networks

To give VMs a second NIC via Multus:

. Uncomment `- name: secondary` in `networks.yaml`
. Add `- secondary` to the VM's `networks:` list in `instances.yaml`

[NOTE]
====
Secondary networks have *no DHCP*.
You must configure a static IP via `userdata:` (cloud-init) in `instances.yaml`
or via a `setup-automation/` script after provisioning.
NetworkPolicy rules in `firewall.yaml` do *not* apply to secondary network traffic.
====

== `firewall.yaml`

`firewall.yaml` defines Kubernetes NetworkPolicy rules for the lab namespace.

[source,yaml]
----
egress:
  - ports:
      - protocol: TCP
        port: 443
----

Rules here are *additive* — they extend the platform defaults, not replace them.

=== Platform defaults (always present)

[cols="1,3"]
|===
| Direction | Rule

| Ingress
| TCP 80, 443, 8080, 7171, 8081, 9000 from anywhere; TCP 22 from the showroom pod

| Egress
| UDP/TCP 5353 (DNS); TCP 22 to other VMs in the namespace; TCP 7171, 8081, 9000 to anywhere
|===

[IMPORTANT]
====
*TCP 443 egress is not in the platform defaults.*
Without it, your `setup-automation/` scripts cannot reach Red Hat CDN, Satellite, or any external HTTPS endpoint.
The example above is the minimum rule needed for almost any lab.

The firewall is applied *after* AgnosticD provisioning (so `packages:` and Satellite registration
are unaffected) but *before* your `setup-automation/` scripts run.
====

== Testing your infrastructure

Once `config/` is defined, test against a live cluster before writing any scripts — it's the fastest way to catch provisioning errors before you have content invested in the lab.

. Go to https://catalog.demo.redhat.com and sign in with SSO
. Click *Catalog*, search for *Developer Experience*
. Select *Developer Experience - RHEL BU* or *Developer Experience - Ansible BU*
. Click the item marked *Development* (red oval)
. Click the blue *Order* button
. Fill in a purpose
. Paste your git repo URL into the repo field
. Paste your branch name into the branch field
. Enable the *Save provision if failed* toggle
. Click *Order*

[TIP]
====
Always enable *Save provision if failed* during development.
It preserves the environment so you can SSH in and debug if provisioning fails.
You can re-use this same mechanism after writing setup scripts and runtime scripts
to test each layer before moving on.
====
